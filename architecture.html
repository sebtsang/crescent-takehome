Reporting architecture

A fundraising reporting surface and an AI assistant that share the same deterministic reporting queries, so there is no separate AI implementation of the fundraising maths. This page shows the data model, where aggregation happens, and the rules that protect the money.

01 · Given, not designed

The data model

Four tables, fixed by the scaffold. The important thing in this diagram is what isn't there: no donors table. The provided model keys donor identity on a normalised email, which is why 251 donations resolve to 223 people.

02 · The load-bearing decision

One aggregation layer, two consumers

The dashboard and the assistant call the same queries rather than keeping two implementations in step by discipline. Everything funnels through one set of deterministic queries before it splits.

03 · Question to answer

How the assistant answers

The model cannot run code. It names a tool, the server runs it, the result goes back, and it either asks again or concludes. Campaign questions take two rounds because the user says “the meal drive” and the tools need an id.

04 · Where the money breaks

Rules that protect the figures

Each of these produces a plausible number when it is broken. That is what makes them dangerous — a wrong total still looks like a total.

R1Only succeeded is raisedDefined once in convex/lib/status.ts — countsAsRaised and partitionByStatus — and applied consistently by every reporting function. Pending, failed and refunded never count. 32 rows, worth $7,710.00, exist in the seed specifically to catch a naive sum.
R2Status is never an inputCallers narrow which rows — campaign, date. They cannot change what raised means. Failed and pending come back as their own named figures instead.
R3Fees are not raisedamountCents is what the org receives; feeCoveredCents is extra the donor paid on top. Raised and charged are different numbers.
R4In this take-home, donor identity is a normalised emailThat comes from the provided data model — the schema has no donors table and keys on donorEmail — not from a general recommendation to identify people by email. Lowercased and trimmed on read. Per-campaign donor counts deliberately do not sum to the org total: 227 across campaigns, 223 overall.
R5Empty buckets are emitted47 of 180 days have no gift. Returning only days that have rows closes the gaps and misdraws the trend.
R6Goal progress is lifetimeA goal is a cumulative target, so filtering to March must not move it. The field is named lifetimeGoalProgressPct so it cannot be read as scoped.
R7Anonymity is stored per gift, resolved per donorThree levels worth separating. Storage: anonymous is a flag on each donation. Derivation: donor-level display anonymity is computed on read, never stored. Product assumption: a donor is shown anonymously only if every succeeded gift is anonymous — two seeded donors gave both ways and resolve to named. The money always counts; only the name is withheld.
R8Ordering is deterministic32 donors tie at exactly $1,000.00. Without a stable tiebreak the dashboard and the assistant each pick a different #7.

Two campaigns are over goal, one has no goal at all, and one has never received a gift. Each is an empty state the dashboard has to render without a blank or a NaN. The data ends 2026-06-29, so any recent window correctly returns zero — which is what makes “how much did we raise last month?” the sharpest test of whether the assistant declines or invents.

Read strategy. Every query collects the whole donations table; the indexes shown in §01 are deliberately unused. computeStats takes the unscoped rows so its coverage field can report the dataset's real bounds even when the scope matches nothing — an indexed range read for an empty July returns no rows, and that guarantee would silently disappear. Correct and instant at 283 rows; it will not survive hundreds of thousands.
